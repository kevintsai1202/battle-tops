# 線上對戰設計（2026-10-01）

## 已確認的決定

- 範圍：房號找朋友對戰（建立房間 → 房號與分享連結 → 朋友加入）。沒有帳號、配對、排行榜。
- 同步模型：伺服器權威＋客戶端預測。依據見 docs/design.md 之後的評估（跨引擎浮點不逐位元相同但差 1e-9；預測誤差約 0；延遲差 100 ms 內勝率影響 < 2 個百分點）。
- 慢動作：伺服器決定撞擊特寫、終結鏡頭與必殺 cut-in 的時間流速，雙方同時看到慢動作。
- 鍵盤加衝刺：Shift＋方向鍵，與手機快甩相同（冷卻 0.9 秒）；CPU 模式也能用。
- 主機：Zeabur，部署在既有的東京騰訊主機（ZeaburOS，2 核；記憶體已用 83%，服務設記憶體上限）。遊戲前端留在 GitHub Pages。

## 架構

```
瀏覽器（GitHub Pages）                          Zeabur 東京主機
┌──────────────────────────────┐   wss://…/ws   ┌──────────────────────────────┐
│ Game（畫面、音效）             │ ◄────────────► │ server/：http（/health）＋ ws  │
│ OnlineSession                 │   JSON 訊息    │ RoomManager → Room            │
│  ├ NetClient（連線、時鐘同步）  │                │  ├ TeamMatch（3 對 3 規則）    │
│  └ Predictor（本機預測＋校正）  │                │  ├ BattleSim（權威模擬 120 Hz）│
└──────────────────────────────┘                │  └ CameraDirector（時間流速）  │
              共用：src/sim/、src/director/、src/net/protocol.ts
```

- 伺服器與前端共用 `src/sim/`（純 TypeScript、沒有外部依賴）、`src/director/director.ts` 與 `src/net/`。伺服器以 Vite SSR 模式打包成單一檔案，執行時只依賴 `ws`。
- 伺服器每秒推進模擬 120 步（依時間流速）；每秒 20 次送出完整模擬快照（含亂數狀態），撞擊、必殺、終結、場地機關、鏡頭導演的事件隨快照一起送。

## 預測與校正（客戶端）

1. 客戶端保有一份本機模擬。收到快照時還原成伺服器狀態，再往前推進「往返時間 × 120 × 時間流速」步：自己用目前的操作（以及還沒被伺服器確認的必殺、衝刺），對手用快照裡伺服器最後收到的操作。
   - 推一個往返時間：快照送到時已經是單程延遲之前的狀態，而自己現在按的操作要再過單程延遲才到伺服器，兩段加起來。
   - 往前推的時間上限 250 ms（`MAX_AHEAD_MS`）：主執行緒卡住時量到的往返時間會暴增（headless 軟體算圖實測 7 秒），照單全收每次要重算上百步、又讓主執行緒更慢。
   - 每幀最多校正一次，用最新的快照（`OnlineSession.flushSnap`）：快照是完整狀態，主執行緒卡住後一次到的多個快照只要最後一個；事件仍逐則處理。
2. 還原造成的位置跳動用畫面偏移慢慢收斂（每秒衰減），看不出來。
3. 特效、音效、語音、鏡頭切換只依伺服器事件觸發（本機預測產生的事件丟棄），不會重複。
4. 必殺、衝刺按下時本機立即套用並送出；伺服器確認前的每次校正，都在還原快照後立刻重新套用（時間點比伺服器實際套用的早一點，等包含它的快照到了就修正）。

## 時間流速

- `CameraDirector` 增加必殺凍結（原本在 game.ts：1.1 秒內 0.12 倍速），CPU 模式與伺服器共用同一份邏輯。
- 伺服器依模擬事件驅動導演，實際時間 × 時間流速 = 模擬時間；導演切換（特寫開始、終結、必殺凍結）當作事件送給客戶端，客戶端的導演照事件切換（不自己判斷門檻與冷卻），鏡頭與伺服器一致。

## 發射

- 伺服器公布「ゴー」的伺服器時間；客戶端用時鐘同步（ping／pong，取往返最短的樣本估算時差）換算成本機時間倒數。
- 客戶端量拉條（時機誤差、長度、速度、世界座標的瞄準角度）後送出；伺服器用「普通」判定視窗算力道，檢查數值範圍。
- 雙方都送出（或「ゴー」後 1.4 秒逾時，逾時的一方以最低力道發射）後，伺服器公布雙方力道、角度與種子，同時開打。

## 座位與視角

- 座位決定開場位置（0 號在左）。每一戰交換座位（第 1、3 戰房主坐 0 號，第 2 戰與延長賽房主坐 1 號；平手重打沿用），抵銷座位偏差。
- 客戶端以「自己」為中心：HUD 左邊永遠是自己（YOU），鏡頭的發射視角轉到自己的背後，瞄準方向、推移方向都依鏡頭換算，不需要鏡像世界。

## 賽制

- 雙方各自組隊（三顆＋零件，零件規則同 CPU 模式），伺服器檢查合法性。雙方都完成後同時公開三顆（出場順序保密），每戰開打前揭曉對陣。
- 場地由房主在房間畫面選（含隨機，開打時抽）。
- 延長賽雙方同時挑，都挑完才公開。
- 結果畫面可以「再來一場」（雙方都按才開始，回到組隊）或離開。

## 斷線

- 每位玩家有重連用的 token。斷線時伺服器暫停模擬（雙方畫面凍結並顯示倒數），30 秒內用 token 重連就繼續；逾時判對方獲勝。
- 房間閒置（大廳 10 分鐘、比賽結束 5 分鐘）自動關閉。

## 安全

- 只接受允許的來源（GitHub Pages 網址與本機開發網址，環境變數設定）。
- 訊息大小上限與每秒訊息數上限；所有數值夾在合法範圍。
- 房號 4 碼，去掉容易混淆的字（I、O、0、1）。

## 訊息（`src/net/protocol.ts`）

客戶端 → 伺服器：`create`、`join`、`resume`（重連）、`arena`、`team`、`launch`、`input`（推移，最多每秒 30 次）、`special`、`dash`、`overtime`、`rematch`、`leave`、`ping`。

伺服器 → 客戶端：`room`（房號、座位、token）、`lobby`（雙方名稱與狀態、場地）、`teams`（雙方公開的隊伍）、`battle`（對陣、座位、雙方規格、「ゴー」時間）、`launched`（力道、角度、種子）、`snap`（快照、事件、時間流速、已處理的操作序號）、`round`（這一戰結果與總分）、`overtime`、`result`、`paused`／`resumed`、`closed`、`error`、`pong`。

## 驗證

- 單元測試：亂數狀態存取、模擬快照還原（還原後繼續推進與原本逐位元相同）、訊息檢查、房間狀態機（假時鐘、假連線：完整一場、斷線暫停與判負、重連、座位輪替、隱藏資訊不外洩）、時鐘同步、預測誤差。
- 整合測試：真的啟動伺服器，兩個 Node 機器人用 WebSocket 打完整一場。
- e2e：兩個瀏覽器分頁對本機伺服器建房、加入、組隊、拉條、對戰、看到一致的結果。
- 部署後：對 Zeabur 伺服器量連線延遲，並用兩個瀏覽器實際對戰一場。

## 進度（2026-10-01）

- 第 1 步 模擬前置：`createRng` 回傳可讀寫狀態的 `SeededRng`；`BattleSim.snapshot()／restore()／fromSnapshot()`（規格只記代號與零件，還原時用 `buildSpec` 重建；經過 JSON 還原後逐步事件完全相同，JSON 約 1.5 KB）；必殺 cut-in 凍結從 game.ts 搬進 `CameraDirector.notifySpecial()`，另加 `forceCloseup／forceFinish`。CPU 模式 e2e（battle.spec）確認行為不變。
- 第 2 步 協定：`src/net/protocol.ts`（訊息型別、`parseClientMessage` 檢查與夾限、隊伍與零件合法性、房號）。
- 第 3 步 房間：`server/src/room.ts`（狀態機；座位↔陣營只經過 `sideOf／seatOf`；暫停時導演時鐘不走、發射階段的「ゴー」與終結停留順延；重連補送完整狀態）、`server/src/manager.ts`（建房、加入、重連、閒置清理）、`server/src/app.ts`（HTTP＋ws、來源檢查、每秒訊息上限、自我修正漂移的主迴圈）。
- 第 4 步 整合測試：`server/tests/integration.test.ts` 真的啟動伺服器（20 倍速），兩個機器人用 CPU 邏輯打完整一場並互為鏡像；斷線重連；來源檢查。全部單元測試 181 個約 13 秒。
- 第 5 步 客戶端：`src/net/client.ts`（連線、ping、自動重連與 resume）、`src/net/clock.ts`、`src/net/predict.ts`、`src/game/online.ts`（`OnlineSession`：房間狀態、推移節流、必殺與衝刺先預測再送、快照校正）；`game.ts` 增加線上房間、組隊、等待、倒數對齊「ゴー」、座位與鏡頭、伺服器事件驅動特效與導演、斷線覆蓋層、結果與再來一場；HUD 增加線上房間畫面與覆蓋層。Shift＋方向鍵衝刺（`e.repeat` 不算，按一次衝一次）。
- 第 6 步 強化：伺服器的訊息與斷線處理包 try/catch（事件監聽器丟出的例外在 Node 會讓整個行程結束、所有房間斷線），並記錄建房、加入、重連；客戶端每幀只用最新快照校正一次、往前推上限 250 ms。
- 第 7 步 雙瀏覽器 e2e（`e2e/online.spec.ts`）：兩個玩家各開一個瀏覽器對本機伺服器（Playwright 一起啟動）。
  - 不能用同一個瀏覽器的兩個 context：它們共用軟體 WebGL 的 GPU 行程，一邊在算圖時另一邊初始化 WebGL 的同步呼叫要排隊，後開的頁面主執行緒卡超過 30 秒。
  - 兩個瀏覽器同時軟體算圖會平分產能（`scripts/net-eval/two-browsers-perf.spec.ts`：1280×720 時各約 1.3～3.8 fps，組隊畫面 evaluate 最久 2.2 秒）；裝置像素比設 0.5（版面不變、畫布 640×360）後各約 4～7 fps。
  - 失敗時印出兩邊的畫面狀態、頁面 console 警告與伺服器紀錄。
  - 衝刺與必殺要在對戰階段才驗得到：這一戰先結束的話下一戰再試，最後一定要驗到（原本的寫法在一戰太短時會直接跳過）。
  - 結果（2026-10-01，本機伺服器）：通過，約 3.9 分鐘；第 1 戰就驗到 B 收到 A 的推移、衝刺、必殺；斷線重連、第 2 戰換座位、結果雙方勝負相反、再來一場、離開都正確。
  - 本機伺服器在兩個瀏覽器同時軟體算圖時記錄了幾次「模擬落後實際時間 30～800 ms，丟棄」：每次推進最多補 60 步（0.5 秒），代表 Node 的事件迴圈有 0.5 秒以上沒被排到（這台機器的 CPU 被兩個軟體算圖的瀏覽器吃滿）。丟掉的時間讓客戶端預測稍微超前，下一個快照就校正回來。
  - 同時跑單元測試會讓 CPU 對打耐久測試逾時（5 秒上限）；單獨跑 195 個全過（約 10 秒）。
